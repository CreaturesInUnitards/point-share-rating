# osyd House Style

Apply these rules by default unless the user explicitly requests otherwise. If
the local project has a more specific `AGENTS.md`, README, or area doc, follow
the local project guidance after understanding these osyd defaults.

## Trigger Guidance

Use this skill when:
- The codebase uses `osyd`.
- The task involves osyd routing, state, lifecycle hooks, vnode semantics,
  page structure, or component architecture.
- The user asks to build, refactor, debug, or explain osyd application code.
- The user asks for osyd idioms or osyd-style refactors.

## Task Tracks

- For app/bootstrap work, focus on startup wiring, root state composition, and
  route setup.
- For page or route-backed refactors, keep route registration, request
  orchestration, state reconciliation, and rendering concerns separated when the
  page is non-trivial.
- For route-backed page tests, keep page-owned tests under a page-root `tests/`
  folder, mirroring `actions/` and `components/` inside `tests/` when helpful.
- For lifecycle, redraw, or state issues, verify which values are render inputs,
  which values are runtime handles, and which writes trigger redraws.
- For component architecture, prefer small osyd-native components with
  explicit props, state, and action boundaries.
- Adapt examples and existing patterns to local project conventions instead of
  copying them blindly.

## Global State

- For route-driven apps, bootstrap with `o.route`, not `o.mount`.
- Pass `o.createState(...)` as the final argument to `o.route` so components receive global state and actions.
- Use `$`-prefixed keys in `defaultState`.
- Global state is the single source of truth for promoted view/data state.
- Use autogenerated setters for single-field updates.
- Use explicit custom actions via `(state, update) => ({ ... })` only for intentful or multi-field transitions.
- `o.createState({ actions })` accepts either one action function or an array of
  action functions.
- Prefer bare action functions for state slices, for example
  `export const jstActions = (state, update) => ({ ... })`.
- Type slice action functions generically over a root state that extends the
  slice state, so root composition can pass bare slice actions directly.
- Compose root state actions as a direct array, for example
  `actions = [authActions, jstActions]`, whenever possible.
- Avoid root action wrappers or object mergers unless there is a real runtime or
  type boundary that cannot be expressed on the slice action type.
- Add `create*Actions(...)` factories only when a slice genuinely needs runtime
  parameters or test-specific dependency injection.
- Keep side-effect callbacks out of `$` state. They are dependencies/effects,
  not app state.
- For effectful slices, production wiring can live in the slice action module if
  doing so does not create import cycles.
- Keep root state modules as thin composition layers for `defaultState` and
  `actions`.
- Avoid compatibility re-exports from root state modules for slice-owned
  symbols.
- Services should import helpers and types from slice modules, not from the root
  state aggregator.
- Do not create single-field custom actions that duplicate autogenerated setters.
- Do not assign global state properties directly.
- Do not use generic patch-style actions as the default write path.
- Do not create mutable local mirrors of promoted global state.
- If a helper needs current state, pass the current values it needs from the call site.
- Keep only runtime-only handles local: DOM refs, `Range`, listener disposers, RAF IDs, timer IDs, and similarly DOM-coupled transient values.

## Local State

- Use `o.getSet` for local state references that child components need to mutate.
- Name `o.getSet` identifiers in camelCase with a `gs` prefix, for example `gsMyValue`.
- Name `o.stream` identifiers in camelCase with an `s` prefix, for example `sMyValue`.
- Treat every `o.getSet(...)` write as a redraw trigger unless redraw is explicitly disabled.

## Vnode and Lifecycle

- `attrs` is not an osyd vnode field; use `props`.
- Refer to vnode shape as `props`, `state`, and `actions`.
- Only use:
  - `view(vnode: Vnode)`
  - `oncreate(vnode: VnodeDOM)`
  - `onbeforeupdate(vnode: VnodeDOM, old: VnodeDOM)`
  - `onupdate(vnode: VnodeDOM)`
  - `onbeforeremove(vnode: VnodeDOM)`
  - `onremove(vnode: VnodeDOM)`
- In `view`, `vnode` is declarative render input.
- In other lifecycle hooks, `vnode` is runtime/rendered context.
- Keep `view` pure.
- Do not use `vnode.dom` in `view`.
- Read changing props inside lifecycle hooks, not in closure setup.
- Avoid `onbeforeupdate` and `onupdate` for routine state sync, persistence, or route writes. Prefer event-driven updates.
- If `onbeforeupdate` or `onupdate` is genuinely needed for reconciliation with external runtime state, guard it with an explicit snapshot or comparison so redraws do not repeat expensive work.

## Component Style

- Prefer parameter-level nested destructuring of only the fields used in the current scope.

```ts
view: ({ props: { p1 }, state: { $foo }, actions: { setFoo } }) => ...
```

- Keep `view` compositional and declarative.
- Do not define helper functions inside `view` except small inline event handlers.
- Local vnode-producing helpers are view functions, not component `view` methods.
- Prefix view function names with `vf`, for example `vfRailButton`.
- Inline single-use type aliases and interfaces at the use site when extraction would add unnecessary indirection. Extract a named type only when it is reused or represents a meaningful shared contract.
- Avoid runtime-wrapper/controller indirection such as `create*Runtime`, `getViewModel`, or `requireLatestState`.
- Avoid indirection in closures. Use an anonymous inline arrow function when there is only a single call site.
- Use lowercase osyd event handler names, not camelCase handler names.
- If a component mostly receives state-derived values and action callbacks, connect it directly to `vnode.state` / `vnode.actions` or split it into smaller domain components.
- Treat large prop bags as a smell.

## Rendering Rules

- `o('')` is the idiomatic default `div`.
- Do not use explicit `div` selectors when the default tag is sufficient.
- Put static classes in the selector, for example `button[type=button][role=button]`, and reserve `className` for dynamic class composition.
- Use varargs for ordinary child vnodes: `o('.panel', header, body, footer)`.
- Do not wrap children in an array just to group them, for example avoid `o('.panel', [header, body])`.
- Use child arrays only for generated lists or when the array is an intentional fragment/key boundary.
- When forwarding component vnode `children` into an element vnode, pass `children` directly. osyd hyperscript and `Vnode.normalizeChildren` already flatten a single child array and normalize primitives/nulls.
- Never transform `children` structure inside a component. Use explicit `slot` props for named placement regions instead.
- Do not use `o.fragment` with an empty props object. Use a plain array.
- Do not mix keyed and unkeyed vnodes in the same sibling list.
- If only one subtree should remount, isolate that keyed vnode in a single-child fragment array.
- When rendering keyed `.map(...)` results in branches with varying sibling shape, wrap the mapped result in a single unkeyed fragment array.

## High-Frequency Interactions

- Prefer native listeners wired through lifecycle hooks over redraw-heavy hyperscript handlers when direct DOM preview is sufficient.
- In closure components, keep stable outer-scope handlers and a `let` DOM ref.
- Register listeners in `oncreate` and always clean them up in `onremove`.
- Do not let `view` and direct DOM handlers fight over the same property during an active interaction.
- Commit canonical state at interaction end.
- Prefer pointer events when feasible.

## App Typing Idiom

```ts
import type { osydComponent } from 'osyd'
import type { Actions, State } from './types/appState'

export type OC<
  Props = object,
  Dom extends Element = Element,
> = osydComponent<Props, State, Actions, Dom>
```

- Define one app-level `OC` alias and reuse it for all components.
- Keep `Dom` defaulted to `Element` for render-only components.
- Pass a concrete DOM type only when lifecycle code needs typed `vnode.dom`, for example `OC<Props, HTMLInputElement>`.
- Public docs and examples should also use the `OC` alias instead of
  `AppComponent`, `OCVnode`, or similarly expanded app-component aliases.
- Do not create separate `OCVnode` or `OCC` aliases.

## Routing

- Prefer `RouteResolver` / `onmatch` for route normalization, canonicalization, and redirect decisions.
- If `onmatch` redirects, do not return the real route component for that pass. Return an inert component instead so the old route does not mount and fire side effects.
- osyd route params arrive decoded. Treat `params.foo` as the decoded value unless you have evidence otherwise.
- Prefer `o.route.set(...)` over `window.history.replaceState(...)` so osyd remains the routing authority and resolvers still run.
- Use `o.route.set(..., { replace: true })` only for canonicalization, redirects, and automatic cleanup of invalid route state.
- For explicit user navigation that should create browser history, prefer `o.route.Link` or `o.route.set(...)` without `replace: true`.

## Route State

- If route-derived UI state is promoted into global app state, keep a thin route-to-state bridge near the route component.
- The bridge should sit at the route boundary and mostly say: route values in, state reconciliation out.
- Pass route params into sync helpers directly. Do not reparse `window.location` inside view components when route props already exist.
- Keep the bridge explicit. Avoid mixing unrelated UI state, request loading, or view-model assembly into it.
- If route validation depends on async-loaded data, do the final reconciliation after load in route-state sync, not in the resolver.
- For route-driven auth bootstrap, mount `o.route` with the shared store first so
  resolvers can render from loading state, then replace the current route after
  bootstrap resolves so resolvers re-run against final auth state.

## Resolver Rendering

- If multiple meaningful route variants render the same component and remount semantics matter, use resolver `render` to key the vnode by route identity.
- Key by the route parts that actually define the view state, for example `file + version`, not by unrelated query noise.
- When the rendered identity depends on async-resolved data, key by the resolved view identity rather than only raw route params.
- Never use time-based keys such as `Date.now()` for normal remount logic. If pending and loaded states legitimately differ, give each state its own stable identity.

## Working Style

- Prefer osyd-native patterns over React-style patterns.
- When generating or editing code, obey the target repository's ESLint and Prettier rules. Run the available formatter/linter when practical, and mirror their output in examples.
- Preserve user edits and keep diffs narrow.
- Follow explicit user guidance over default conventions when they conflict.
